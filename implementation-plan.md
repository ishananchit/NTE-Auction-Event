# Going, Going, Gone! — Implementation Plan

Staged build order for the local recreation. Mechanics/rules are specced in `going-going-gone-mechanics.md`; item/assistant/device data is in `assistants-and-devices.json` and `collectibles-template.xlsx`. This doc is just the *build order and scope per stage* — not a mechanics reference, don't duplicate rule detail here.

Each stage should be playable/testable on its own before moving to the next (Stages 1-3: purely locally, no network; Stage 4 is deliberately the one that adds networking).

**UI philosophy:** the UI does **not** need to look like the reference screenshots. We'll keep major components in roughly similar positions/layout (e.g. grid on the right, player/round info on the left) for familiarity, but the priority throughout is functionality, not visual fidelity. Don't spend effort matching exact colors/art/spacing from the source game.

---

## Stage 1 — Auction lot + grid system ✅ DONE

- Lot generation: random lot size (30–60), weighted random sampling with replacement over the collectible pool to fill it (see mechanics doc §8 for the exact algorithm). — `app/js/lotGenerator.js`
- Grid packing: fit all the lot's item shapes into a rectangular grid without overlap, via a shelf/first-fit-decreasing-height heuristic (10 columns wide, rows grow as needed). — `app/js/gridPacker.js`
- Grid rendering: items shown as colored blocks by rarity, no images — just name/rarity color/shape. Implemented the full reveal-state model (§5a) as two independent booleans (`rarityKnown`, `shapeKnown`) plus `fullyRevealed`, rendered as hidden / single-cell rarity dot / grey silhouette outline / colored silhouette / fully revealed (name shown). — `app/js/revealState.js`, `app/js/grid.js`
- Collectibles Index screen: browsable catalog with Rarity/Shape filters (§5e), usable standalone against the static item pool. Shapes are plain sizeX×sizeY rectangles (no irregular-shape data exists yet), so the shape filter is an exact WxH match rather than the ~25-shape palette. — `app/js/collectiblesIndex.js`
- Data pipeline: `scripts/convert_collectibles.py` regenerates `app/data/collectibles.json` from `collectibles-template.xlsx` — rerun it any time the spreadsheet changes.
- **Done when:** can generate a random lot, see it laid out on a grid, and manually toggle/inspect every item's reveal state and see it render correctly. No bidding, no rounds, no networking yet. — verified in a real browser (click-through of all 5 reveal states, Collectibles Index filtering), not just code review; one real bug (Collectibles Index panel losing its positioning classes) was caught and fixed this way.

**How to run:** from `app/`, start any static file server (e.g. `python -m http.server 8642`) and open `http://localhost:8642/index.html` — must be served over `http://`, not opened as a `file://` path, since it uses ES modules + `fetch`.

## Stage 2 — Rounds + bidding logic ✅ DONE

- Core game logic split into a pure, UI-independent engine (`app/js/auctionEngine.js` + `app/js/poolStats.js` + `app/js/auctioneerIntel.js`) driven entirely by explicit calls (`createMatch` / `placeBid` / `resolveRound`), no timers or DOM inside it — same separation-of-concerns approach as Stage 1's grid logic, and it's what made thorough automated testing possible (see below).
- Round loop: 6 rounds, single main bid UI with 6 bid-slots per player throughout (§3/§8), per-round 60s timer (`main.js`) with Bid / Pass actions (Device is stubbed — button intentionally not wired up yet, lands in Stage 3).
- Win-condition thresholds per round (2.0x / 1.6x / 1.3x / 1.1x / highest-bid-wins / Round 6 tiebreak restricted to the tied players only) — §4.
- Auctioneer Public Intel: one free baseline reveal per round, randomly drawn from the stat-type pool, pushed to a persistent log (§5b).
- Current Estimate: computed live from whatever's been revealed on the grid so far (§5a's formula, now finalized — see mechanics doc §8).
- Resolution: Final Sale Price, Actual Value, Earnings (can be negative); instant cash-out straight to the winner's balance; 10% overpay spillover to the other 3 players (§7).
- Local play: Player 1 is human-controlled by default, Players 2–4 are simple placeholder bots (any seat's Human/Bot toggle can be flipped for local hotseat testing, sequential-not-blind — see mechanics doc §8 caveat).
- **Done when:** a full lot can be bid on end-to-end by 4 local/hotseat players (or simple stand-ins for the other 3), rounds advance correctly, and payout math resolves correctly including the spillover rule. — Verified two ways: (1) a Node regression suite (`scripts/test_auction_engine.mjs`, 36 checks incl. 200 randomized full matches) covering every round-resolution edge case (instant win, threshold miss, sole bidder, exact tie, Round 5→6 tiebreak, still-tied-after-tiebreak, nobody-ever-bids, over-balance rejection, payout math both directions); (2) a real browser session clicking through actual matches, confirming the UI wiring matches the engine (displayed balances/Earnings/spillover matched exactly, Current Estimate responded correctly to revealed items, round/log/bid-slot display all correct).

**A few things the mechanics doc didn't pin down were decided here** (all recorded in `going-going-gone-mechanics.md` §8): the exact Current Estimate formula, that "second-highest bid" is scoped per-round (defaulting to 0 with <2 bidders), Auctioneer Intel's random stat-type selection, and that local multi-human hotseat isn't truly blind yet (a known limitation until Stage 4 networking).

**`app/js/config.js`** is the one place for numbers we expect to keep tuning by hand during dev/testing (as opposed to `going-going-gone-mechanics.md`, which is about what's *accurate* to the source game). Currently holds: `STARTING_BALANCE` (also the per-match max bid cap), `AUCTIONEER_INTEL_ROUNDS` (which rounds get a new intel entry — confirmed in-game as sparse, not every round), `OVERPAY_SPILLOVER_RATE`, `ROUND_THRESHOLDS`, `ROUND_MS`. Add new tunables here as they come up rather than inlining magic numbers elsewhere.

## Stage 3 — Assistants + devices ✅ DONE

- Generic effect dispatch: ~7 reusable handlers (`app/js/effects.js`) covering the full glossary — Evaluation, Size, "rarity+silhouette together", Appraisal, Count, Valuation, Average Value, Slot, plus a text-only edge case for the one device with no matching reveal-state — backed by a small set of reusable item-selection strategies (`app/js/itemSelection.js`: random / by-rarity / largest-footprint / highest-rarity / known-rarity-unknown-shape / all). No device or assistant has its own bespoke function.
- **All 17 Device Sets** (not just 2–3) turned into structured data (`app/js/deviceCatalog.js`) — went ahead and did the full set since, once the dispatch pattern was proven, the rest was pure data entry anyway.
- **All 8 Auction Assistants** turned into structured per-round schedules (`app/js/assistantCatalog.js`), including the trickier ones: Chiz's "reveal these same items later" callback (remember/recall via per-player match memory), Hotori's "all items with known rarity" conditional-on-current-state selection, Hathor's "reveal everything" at Round 5.
- Pre-match setup UI: each of the 4 seats independently picks an assistant (or random) and any number of Device Sets, applied on the next "New match" — no currency cost yet (per user: "don't need to add buy function yet, just choosing before match is fine"). Devices are usable during any round (not tied to a specific round), single-use each, via a "Use" button next to the round's bid form.
- Added the **2 additional Auctioneer Intel reveal-card types** the user confirmed exist in-game (rarity of 2 random items / silhouette of 2 random items) to the intel pool — these reuse the exact same Evaluation/Size handlers, not a separate implementation.
- **Done when:** a match can be played with an assistant active and at least one purchased device set usable mid-round, reveals correctly updating grid state from Stage 1. — Verified two ways: (1) a Node regression suite (`scripts/test_devices_assistants.mjs`, 28 checks) covering catalog integrity, device use + reuse rejection, category-filter no-op behavior, several assistants' exact schedules (including Chiz's remember/recall producing the *same* 8 items on replay), the new intel cards actually firing, and 60 randomized full matches with random assistants/devices for all 4 players; (2) a live browser session — configured a seat's assistant + device set via the setup UI, started a match, watched all 4 seats' assistants fire correctly into the log, used a device mid-round and watched it mark itself used and update the grid + Current Estimate.

**A few ability texts needed an interpretive call** (all recorded in `going-going-gone-mechanics.md` §8): Adler/Edgar grant both reveal flags together per rarity tier; Jiuyuan's start-of-match ability is shape-only; category-filtered devices are currently no-ops (category data isn't in the spreadsheet yet); reveal effects generally avoid re-targeting already-known items by default.

**Post-Stage-3 fixes** (user testing caught real issues, all now fixed and covered by regression tests):
- **Reveals are private per-player, not shared** (§5 "information privacy" — a genuine mechanics correction, not a design choice: only Auctioneer Public Intel is visible to everyone; Assistant/Device reveals are visible only to whoever triggered them). This was a real architecture change: every item now tracks a `publicReveal` (Auctioneer Intel only) plus a `privateReveal` per player (Assistant/Devices only) — see `app/js/revealAccess.js`. Current Estimate, the grid, and the reveal log are now all computed **per viewed player**, not once globally. A "Viewing grid as" selector in the match UI lets you inspect any seat's actual view; a separate Debug "God view" toggle shows the union of everyone's knowledge for testing/verification, entirely separate from what a real player would see.
- **Setup now properly gates the match** — a dedicated full-page Setup screen (assistant/devices/Human-per-seat) is the only thing shown until "Start Match" is clicked; the bidding UI/grid don't exist yet at that point. "End match" returns to Setup for the next match.
- **Ambiguous log text fixed**: effects that target a specific rarity tier (Adler, Edgar) now name the rarity in their log line (e.g. "9 White-rarity collectible(s)") instead of a generic count that looked like a duplicate firing when two different rarities happened to have the same count.

## Stage 4 — Networking / PvP ✅ DONE

- **Backend:** Firestore (chosen over Realtime Database — see conversation: our state is naturally "one document per match," updates are discrete/event-driven not high-frequency, and the free tier is way more than a friend group needs). No Firebase Auth (deliberately skipped for now — a random per-tab id in `sessionStorage` stands in for identity; privacy is enforced by what a client chooses to render, not by security rules — an accepted risk for a private friends game, same one already noted for local play).
- **Data model:** one Firestore document per room at `rooms/{code}` holds `{roomCode, hostClientId, phase: "lobby"|"match", seats, match}` — the entire match state (lot, bids, logs, players) is a single nested object on that doc. Confirmed comfortably under Firestore's 1MiB limit (~28KB for a full match). An `actions` subcollection under the room doc is used as an intent queue (see below). — `app/js/roomSync.js`
- **Joining flow:** short shareable room code (e.g. `85YU7`), not a lobby/matchmaking system — one player creates a room and gets a code, others type it in to join. — `app/js/roomCode.js`
- **Host-authoritative sync:** whichever client created the room is the only one that actually runs the engine (`placeBid`/`useDevice`/`resolveRound`) and writes the authoritative `match` state back to Firestore; every other client (host included, for uniform code) submits intents into the `actions` subcollection instead of mutating anything directly. The host subscribes to that queue, applies each pending action, checks if the round should resolve, and pushes the updated state — which every client (via a live `onSnapshot` listener) picks up and renders. Bots are host-simulated (not real network clients) and get applied directly, no queue round-trip. Chosen over a Cloud Functions backend specifically to avoid needing a paid Blaze plan; the accepted tradeoff is that the match stalls if the host's tab closes mid-game (fine for a casual friend game, not addressed further here).
- **Round timer:** the host stamps `match.roundDeadline` (an epoch-ms field) into the synced match whenever a round starts; every client runs a lightweight shared tick that (a) always updates the countdown display from that field, and (b) *only if host* force-passes anyone who hasn't acted once the deadline passes.
- **Firestore serializability landmine, fixed before any networking code was written:** the grid-packing layout used to be a `Map` keyed by item object references, computed lazily per-client on render. Neither part survives Firestore (Maps aren't serializable, and independent per-client packing would have made different players see different random layouts for the same lot). Fixed by computing the packing once at lot-generation time and storing it as a plain `{[instanceId]: {x,y}}` object directly on the lot — `app/js/gridPacker.js` / `app/js/lotGenerator.js`. Verified the *entire* match object round-trips cleanly through `JSON.parse(JSON.stringify(...))` with no `Map`/`Set`/`undefined`/function values anywhere.
- **Client identity uses `sessionStorage`, not `localStorage`** — `localStorage` is shared across every tab of the same origin, which would've made multiple tabs on one machine collide on the same identity and broken the "open several tabs on my own computer to test multiplayer" workflow this needs to support. `sessionStorage` is per-tab. — `app/js/clientIdentity.js`
- **UI:** three-screen flow — Landing (name + create/join) → Lobby (per-seat assistant/device/human-bot setup, live-synced, only your own seat editable, empty seats auto-filled with bots on start) → Match (same rendering as Stage 3, now driven by the synced room doc instead of local state; a "Viewing grid as" selector is restricted to your own seat + bot seats, since peeking at another real player's private view would defeat §8's privacy rule).
- **Done when:** 4 separate browsers/devices can join the same match and play a full auction together with correctly synced state. — Verified against the **real Firestore project** (no emulator set up): (1) a 12-check integration test of the room/actions read-write layer itself; (2) genuine two-real-browser-tab tests (separate CDP targets, separate sessionStorage identities, talking to each other only through Firestore, exactly like two different computers would) covering room creation, live lobby seat sync, match start, cross-client bid sync, and — critically — confirming public logs match byte-for-byte across clients while private logs differ, proving the privacy split actually holds over the network, not just locally; (3) a full match played to completion across both tabs, host ending the match, and both tabs correctly returning to the lobby. One real bug was caught this way and fixed: bot-scheduling `setTimeout` callbacks compared `state.match !== match` to detect staleness, which worked in the local build (mutated in place) but broke over the network (a fresh object arrives on every snapshot) — bots were silently never acting. Fixed by re-reading `state.match` fresh inside the callback instead of relying on the closed-over reference.

**How to run/test multiplayer yourself:** same static server as before (`python -m http.server` from `app/`), just open multiple tabs/windows pointed at it — each tab is naturally its own player since identity is per-tab. No deploying required to fully test this; GitHub Pages only matters once you want a public URL for friends to open on their own machines (same code, same Firestore project either way).

**Post-Stage-4 fix — bidding wasn't actually simultaneous/blind:** the first networked build had drifted from what §4 already correctly specified. It (1) only let one player act at a time in seat order (`p1` had to bid before `p2`'s form even appeared), and (2) revealed each bid's exact amount to everyone the instant it was submitted, instead of after the round resolves. Both fixed, purely in rendering — the host still needs real bid values to resolve rounds, so no engine/sync change was needed:
- Any eligible player who hasn't yet acted this round now sees their own bid form immediately, independent of whether others have acted — no more turn order.
- A player's bid amount for the round **currently in progress** is shown as "locked in" (masked) to everyone except themselves until the round resolves; once it resolves (round advances or match ends), that round's amounts become visible to everyone, matching "the reveal happens together after the round ends." Same client-side-only privacy model as §8's reveal split (not enforced by security rules).
- The quick-fill "Nx current top" button was itself a leak (it read other players' live bids to compute its target) — changed to be based on Current Estimate instead (info the player legitimately has), with a note clarifying it's a rough guide, not a guaranteed-clearing amount, since the real threshold is relative to the (hidden) second-highest bid.
- Verified with a real two-tab test: both players get their bid form at the same time, a submitted amount is masked on the other tab until resolution, and is correctly revealed to both afterward.

**Post-Stage-4 UI pass — assistant/device info in the lobby:** the pre-match seat setup previously used a bare `<select>` for the assistant and a plain checkbox list for device sets, with no way to see what anything actually does before picking it (user feedback, with in-game screenshots of "Auction Assistant List" and "Device Set" popups as a UX reference). Reworked the lobby (`app/js/main.js` `renderLobby()` + new helpers, `app/style.css`):
- `assistantCatalog.js` and `deviceCatalog.js` gained human-readable text fields (`ability` per assistant, `description` per device set, `effect` per individual device) pulled from `assistants-and-devices.json`, which already had this copy — previously unused by the app.
- Own seat is now a browsable picker: a scrollable list of assistants/device sets on the left, an info panel on the right showing flavor quote + skill + full ability text (assistants) or description + per-device effect breakdown (device sets) for whichever item was last clicked. Assistant choice is single-select (click = pick); device sets keep independent checkboxes (click the name to preview without buying, check the box to buy) — mirrors the reference screenshots' portrait-list + detail-pane pattern without copying it pixel-for-pixel (no character art here).
- The 3 other seats (which only ever showed name/assistant/device-count, never editable) were shrunk to compact one-line cards to give the player's own seat the space it needed.
- Verified via a CDP-driven browser test against the real Firestore project (create room, click through the assistant/device lists, confirm detail panel content and screenshot the layout), then removed the throwaway test script per the project's convention.
- Follow-up: device sets were changed from multi-select (checkboxes, could buy several) to single-select, mirroring the assistant picker exactly (a `(none)` option instead of `(random)`, clicking replaces the previous choice rather than adding to it) — `seats.N.deviceSetNames` in Firestore is still an array for compatibility with `instantiateDevices`, just constrained to 0 or 1 entries from the UI now.

**Post-Stage-4 UI pass — main match screen layout (`app/style.css`, `app/index.html`, `app/js/main.js`):** on a wide screen the grid sat left-aligned immediately after the center column instead of using the available width, the players panel was cramped enough that large bid amounts (up to the 10,000,000 balance cap) risked getting clipped, and the round/intel panel, bid form, and device inventory were all crammed into a visually merged block. Fixed purely as layout/markup changes, no engine/game-logic change:
- `.grid-panel` is now a flex container with `justify-content: flex-end`, so `.grid` (a fixed `width: max-content` block) sits flush against the right edge of the available space instead of floating right after the center panel with a large dead gap.
- `.side-panel` widened 280px → 460px, with `.player-card` and `.bid-slot` font sizes/padding increased to match — verified via a real running match (headless-browser test) that a 7-digit bid amount and an 8-digit balance both render without clipping.
- The devices list moved out of `#bid-entry-panel` into its own `#devices-panel` element/`.panel-block`, and `.center-panel` switched from each block's own `margin-bottom` to a `gap` on the flex column, so round/intel, bid entry, and devices now render as three visually distinct cards with even spacing instead of one merged block.
- Follow-up: the center panel was glued directly against the players panel, dumping all the leftover width into one gap before the grid. `main` changed from a plain flex row to `display: grid; grid-template-columns: 460px 1fr 460px 1fr auto;` (players panel / spacer / center panel, widened 340px → 460px / spacer / grid).
- Follow-up correction: the first attempt (`460px 1fr 460px 1fr`, grid-panel as the last `1fr` column with `justify-content: flex-end`) still looked off-center — caught by the user from a screenshot. Cause: the grid box is a *fixed* size (10 columns × 32px cells = 356px — see `grid.js` `CELL_PX` / `config.js` `GRID_WIDTH`; only its height varies by lot), but its column was a 500px-wide `1fr` track, so ~124px of invisible dead space sat between the center panel and the visible grid box on the right, while the left spacer was a genuinely empty 500px — same column widths, very different visible gaps. Fixed by sizing the grid's column to `auto` (hugs the grid tightly, ~396px = 356px + the panel's own 1.25rem×2 padding) and dropping the flex/justify-end on `.grid-panel` (no longer needed — no leftover space inside that column to align within). With the grid-panel column tight, the two `1fr` columns are the *only* leftover space and split evenly. Verified via `getBoundingClientRect()` on a live match at a 1920px viewport: 460 / 302 / 460 / 302 / 396 px, i.e. both spacer gaps are exactly 302px, and the grid box still ends flush against the right edge (right: 1900px, matching its own 20px padding to the 1920px viewport edge).

**Post-Stage-4 UI pass — color theme (`app/style.css`, `app/index.html`, `app/js/main.js`):** the whole app (prep/lobby screens and the match screen) was flat dark-grey-on-black with white text throughout — functional but visually monotone. Redesigned around a two-layer system, keeping the grid itself and the outer page canvas untouched per explicit instruction:
- New CSS custom properties at `:root`: a single warm-white `--card-bg`/`--card-border`/`--ink`/`--ink-soft` set for anything nested one level inside a section (intel entries, bid slots, picker items, player cards, inputs/selects, device rows — kept one consistent hue everywhere so nested content reads clearly regardless of which section it's in), plus 7 pastel "section tint" pairs (`--tint-{blue,green,amber,purple,rose,gold,slate}-{bg,border,ink}`) exposed through reusable `.tint-*` utility classes that set `--panel-bg`/`--panel-border`/`--panel-ink`, consumed by `.panel-block` and every other section-level container (`.landing-action-block`, `.lobby-my-seat`, `.collectibles-index-overlay`) via `var(--panel-bg, var(--tint-slate-bg))`-style fallbacks.
- Each `.panel-block` in `index.html` got an explicit tint class so every section is visually distinct: Match=slate, Players=green, Debug=rose, Collectibles Index=purple, Round/Intel=blue, Bid Action=amber, Devices=purple, Result=gold. Landing screen's two action blocks are green (create) / blue (join); the lobby's own-seat panel is blue.
- Semantic accent colors (positive/negative earnings, errors, winner/passed/locked bid-slot states) were re-tuned from light-on-dark to darker, saturated variants now that they render on light backgrounds instead of near-black ones.
- Found via a headless-browser screenshot during verification: the empty `#bid-entry-panel` (no longer hidden via `display:none` after this pass added a `.tint-amber` background to it) showed as a stray colored bar once a round ended. Fixed by giving `renderBidEntry()` the same show/hide-via-`style.display` pattern already used for `#devices-panel`/`#result-panel`.
- Verified with headless-browser screenshots across landing, lobby (with an assistant + device set picked, so selected/detail states show), and match screens (bidding, debug/god-view + Collectibles Index open, and a resolved round showing the gold result panel) — including a full computed-style + cropped-screenshot check on the Collectibles Index overlay after an initial full-page screenshot made it look unstyled at a glance (it wasn't — `getComputedStyle` confirmed the correct tint the whole time; a cropped close-up screenshot confirmed it visually too).

**Post-Stage-4 feature — session wallet + paid match entry/devices:** implements the "Device Set purchasing (currency cost + persistent inventory across matches)" item that was explicitly deferred back in Stage 3, at the scope the user actually asked for now (a per-room session currency, not a cross-session/cross-room persistent inventory — there's still no backend/auth, so nothing survives a page reload into a new room).
- New config constants: `STARTING_SESSION_BALANCE = 5_000_000` (granted once when a seat is claimed) and `STARTING_MATCH_FEE = 5_000` (charged to every seated non-bot player when the host starts a match, floored at 0 rather than blocking start). Both distinct from the existing `STARTING_BALANCE` (10,000,000), which is still the unrelated per-match *auction bidding* balance that resets every match — this is a separate meta-currency layered on top, matching the reference game's "My Assets" wallet.
- New `seats.N.balance` field on the room doc, set on `claimSeat` and otherwise only ever touched by explicit spends — `hostStartMatch`/`hostEndMatch` never reset seats, so it naturally persists across matches within the same room for as long as that browser tab/session holds the seat.
- Lobby UX changed from click-to-instantly-equip to a browse-then-confirm model for both pickers, matching the reference game's list+detail+Confirm pattern: clicking an assistant or device set now only updates the detail panel preview (`.picker-item.previewing`, blue border) — the actually-equipped choice (`seats.N.assistantName`/`deviceSetNames`, `.picker-item.selected`, gold fill) only changes when the new **Confirm** (assistant, free) or **Buy** (device set, costs its listed price) button is clicked. Both buttons disable themselves with a "Confirmed"/"Equipped" label when the preview already matches what's equipped.
- Device-set buying is a refund-then-charge swap (`computeDeviceBuyState`): switching to a different set before the match starts refunds the currently-equipped set's price and charges the new one, so freely reconsidering in the lobby never costs more than the one set you land on; the Buy button shows the net cost/refund and disables itself with an inline error if the wallet can't cover it.
- Verified with a headless-browser run through the whole flow against the real Firestore project: preview vs. equipped visual states, Confirm/Buy buttons enabling/disabling correctly, a device-set switch producing the exact expected net-cost wallet deduction, the match-start fee being deducted, and the post-fee balance still being there (further reduced by the next fee) after actually starting and ending a match — i.e. genuine persistence across matches in one room, not just across renders.

**Post-Stage-4 fix — the match itself still used a fresh 10,000,000, not the wallet (user-reported bug):** the wallet feature above only ever wrote to `seats.N.balance`; `hostStartMatch` still called `makePlayers(4, STARTING_BALANCE)` and never touched `player.balance` for real players, so the actual in-match bidding balance (and its display) stayed a flat 10,000,000 regardless of what the wallet said — spending on a device set was real, but starting a match didn't reflect it. Fixed by making a real player's match balance *be* their post-entry-fee wallet balance (bots still get `STARTING_BALANCE`), matching the reference game's single "My Assets" pool used for both device purchases and bidding, and banking `player.balance` (which the auction engine already keeps correct — `resolveRound` applies earnings/spillover directly to it) back to `seats.N.balance` via a new `computeWalletSyncFields()` helper, called both when a match concludes naturally (sold/unsold, inside `hostResolveIfReadyAndSync`) and when the host ends one early (`hostEndMatch`) — so wins, losses, and spillover now actually persist into the next match's starting wallet, not just the pre-match spend. `writeMatchState`/`returnRoomToLobby` in `roomSync.js` were folded into direct `updateRoomFields` calls at their one call site each (needed to attach the wallet fields to the same write) and removed as now-dead wrappers.
- Same report also flagged that every player's balance was publicly visible in the match screen's Players panel. Fixed by masking it the same way bid amounts are masked (§8): only the currently-"Viewing grid as" player's balance renders as a real number (or all of them, in God View/debug) — everyone else shows an italicized "hidden". Verified live: my own balance renders correctly, bots show "hidden" until I switch "Viewing grid as" to that bot, at which point that bot's real balance appears and mine flips to hidden.

**Post-Stage-4 UI pass — device tooltips during a match:** the in-match Devices panel listed each owned device by name only, with no way to see what it actually does short of remembering from the lobby's device-set detail view. Added a native `title` attribute to each `.device-row` (in `renderBidEntry()`'s `deviceRows` in `main.js`), sourced from the same `DEVICE_DEFINITIONS[name].effect` text already used for the lobby's device detail panel — hovering now shows the description as a browser tooltip, the same mechanism already used for grid cells (`grid.js`'s `el.title = ...`). Added `cursor: help` on `.device-row` as a hover affordance. Verified the `title` attribute resolves to the correct effect text for a real device set in a live match.

Darkened every `--tint-*-bg`/`--tint-*-border` pair and `--card-bg`/`--card-border` in `:root` (lightness pulled down roughly 10-15%, same hues), plus the handful of colors that were hardcoded instead of using those variables: `.field-row input`/`.landing-action-block input` (were a near-white `#fffdf7`, now just `var(--card-bg)`), `.picker-item.selected`'s highlight, `.bid-slot`'s background, and a few gold/tan border accents (`.picker-item:hover`, `.player-card.acted`, `.bid-slot.winner`). Text ink colors (`--ink`/`--ink-soft`) were left as-is — only the light backgrounds were the complaint.

**Post-Stage-4 fix — grid size leaked lot info (user-reported):** the grid's rendered height tracked each lot's actual packed height (which depends on item count/sizes), so a small/cheap lot rendered as a visibly shorter grid box than a large one — an unintended tell available before anything was revealed. Fixed by making the grid's row count a fixed constant (`GRID_FIXED_HEIGHT` in `config.js`) instead of the lot's own `gridHeight`; unused rows beyond what a given lot needs just render as empty dark background, and `.grid-panel`'s `auto`-sized column (see the earlier centering fix) now hugs a box that's always the same size. Value derivation: the largest collectible in the pool is 5×5, two of which pack perfectly side-by-side across the 10-wide grid with zero waste, so the worst case at `LOT_MAX_ITEMS` items is exactly `ceil(LOT_MAX_ITEMS / 2) * 5` rows — empirically confirmed against `gridPacker.js` with that exact pathological all-5×5 input plus several other adversarial size mixes (none exceeded it), then given a +20 row margin on top.
- Also moved the lot's item-count range (previously hardcoded as `{ minSize: 30, maxSize: 60 }` inline at every call site — `main.js`, `lotGenerator.js`'s own defaults, and both test scripts) into `config.js` as `LOT_MIN_ITEMS`/`LOT_MAX_ITEMS`, which `GRID_FIXED_HEIGHT`'s derivation now reads from directly, so the two stay in sync if the range ever changes.
- Drive-by fix found while touching the test scripts: `test_auction_engine.mjs`'s Test 10 hardcoded an expected 10% overpay-spillover share, which had gone stale against `config.js`'s `OVERPAY_SPILLOVER_RATE` (now 0.2, changed independently by the user) and was failing. Changed it to read `OVERPAY_SPILLOVER_RATE` from config instead of a hardcoded literal, the same fix shape as the lot-size one.
- Verified live: `.grid`'s rendered pixel size (5796×356px, 170 rows) is identical across several consecutive matches with different randomized lots. Both regression suites pass (36 + 38).

**Post-Stage-4 UI pass — hiding testing-only UI (not deleting):** two pieces of UI were built for solo/local testing rather than real multiplayer play, and are now hidden (via `style="display:none"` on their container, no JS touched) rather than removed, so they're trivially available again from devtools if needed later:
- The **Debug** panel (God-view checkbox) — `state.debug` and its rendering logic are unchanged, just not shown.
- The **"Viewing grid as"** dropdown, on the explicit reasoning that a real player should only ever see their own POV — peeking at a bot's perspective was a testing convenience, not a real feature. `state.viewingPlayerId` now just stays at `myPlayerId` for the whole match for a real seated player, since nothing in the UI can change it anymore (God View, if re-enabled via devtools, still reveals every player's info regardless — unaffected). Relabeled the two bits of copy that referenced "the viewed player" ("Current Estimate (for the viewed player)" → "Current Estimate", "viewed player's own Assistant/Device reveals" → "your own Assistant/Device reveals") since it's now always you.

**Post-Stage-4 fix — Current Estimate was a rough average, not a real floor (user-reported):** the previous formula added the *pool-wide average* value for a rarity/size once any single item's rarity or shape was known — informative, but not what the user wanted: a genuine guaranteed-minimum reading using only what's visible on the grid (no aggregate intel/device stats folded in, per explicit instruction). Rewrote `computeCurrentEstimate()` in `poolStats.js`:
- Fully revealed items still contribute their exact price.
- Rarity **and** shape both known (not identified) now contributes the cheapest pool item matching that *exact* size and rarity together (the tightest defensible floor) — e.g. "1×3 and Gold" contributes the cheapest 1×3 Gold item in the whole pool, not an average.
- Rarity known only contributes the cheapest item of that rarity; shape known only contributes the cheapest item of that exact size.
- Unrevealed items still contribute 0.
- `computePoolStats()` now precomputes `minByRarity`/`minBySize`/`minBySizeRarity` lookup tables alongside the pre-existing `rarityAverages`/`poolAverage` (kept as-is — `bots.js`'s blind-bidding heuristic depends on `poolAverage` for an unrelated calculation, not touched).
- Verified with a direct unit check against the real collectible pool: hand-computed expected minimums for Gold-rarity, 2×2, and 1×3-Gold items matched the new lookup tables exactly, and a synthetic 4-item lot (one rarity-only reveal, one shape-only, one rarity+shape, one untouched) produced the exact expected sum. Confirmed live in a real match too. Both regression suites still pass (36 + 38) — the one existing Current-Estimate test only checked a relative property (owner's estimate > non-owner's after a private reveal), which still holds.

**Post-Stage-4 verification — Jiuyuan's assistant schedule (user asked to confirm, not a bug report):** simulated a full match with Jiuyuan assigned to p1 and isolated exactly what his private reveals granted, round by round (separating them from the also-firing public Auctioneer Intel, which was initially conflating the picture). Confirmed correct: round 1 grants silhouette-only (`shapeKnown`, not `rarityKnown`) of exactly 1 item, and it's always from the lot's actual highest rarity tier present (`selectHighestRarity` in `itemSelection.js` walks `RARITY_ORDER` from Red down to White and returns the first non-empty tier); rounds 2-5 each grant rarity+silhouette (`rarityAndSize`) of exactly 1 new random item, never repeating an already-targeted one (`selectRandom`'s `isKnown` exclusion). No changes needed.

**Post-Stage-4 feature — full lot reveal once the auction ends:** previously, once a match resolved (sold or unsold), the grid kept rendering each item according to whatever partial reveal state existed at the moment bidding stopped — most items stayed hidden/partial forever, even though there was nothing left to protect. The "Actual Value" (total price) was already shown in the result panel, but individual item identities weren't. Added a `revealAll` option to `renderGrid()` (`grid.js`): when true, every item renders with a synthetic `{rarityKnown: true, shapeKnown: true, fullyRevealed: true}` regardless of what was actually known to anyone during play — a stronger guarantee than the existing debug/god-view's `omniscientReveal` (which only shows what *was* revealed to *someone*, still leaving never-touched items hidden). `main.js`'s `render()` now passes `revealAll: match.status !== "bidding"`, so this kicks in for both "sold" and "unsold" outcomes once bidding is fully over. Kept separate from `debug` so the click-to-cycle testing affordance stays debug-only. Verified live: a match with only 5 of 39 items partially known during play showed all 39 as fully-revealed (name + price) cells immediately once the lot sold.

**Post-Stage-4 tuning — bot bid sizing (`bots.js`):** when a bot has a nonzero Current Estimate, its bid multiplier changed from a wide 0.5x-3.5x spread to a tighter 1x-2x (`PASS_CHANCE`/pass behavior and the separate 0-estimate "blind guess" fallback, which isn't based on Current Estimate at all, are unchanged). Verified with 2000 simulated decisions against a real mid-match estimate: every non-pass bid landed within [1.0x, 2.0x] and the ~30% pass rate was unaffected.

**Post-Stage-4 fix — removed the "blind guess" bid entirely (user-reported):** user saw a bot bid ~2.8M on a lot actually worth ~900k and asked whether Current Estimate was being computed differently for bots. It isn't (`bots.js` calls the exact same `currentEstimate()` humans see) — traced it instead to the *other* branch, used only when a bot has zero info revealed to it: `blindEstimate = poolStats.poolAverage * lot.items.length`. `poolAverage` (245,166) is badly skewed by just 2 extreme-outlier items (22.6M and 20.1M) out of 200, versus a pool median of only ~4,000 — so for a typical 30-60 item lot, `blindEstimate` alone comes out to 7.3M-14.7M, making even the "cautious" 0.1x-0.8x slice of it (735k-11.7M) wildly disconnected from what any specific lot is actually worth. Per explicit user instruction, removed this fallback entirely rather than fixing the underlying statistic (e.g. switching to a median) — a bot with zero information now simply passes (bid 0) every time, full stop. Verified: forced a match where a bot's Current Estimate was genuinely 0 and confirmed 1000/1000 decisions returned exactly 0.

- `main.js` added a shared `openCollectiblesIndex(filters)` — used by the grid's `onCellPeek` (always force-opens/re-filters) and refactored into the existing sidebar button's handler too (still toggles open/closed with no filter, unchanged behavior there).
- Verified two ways: end-to-end through a real match (Edgar's assistant reveals rarity+shape together — clicking a resulting cell opened the index pre-filtered to that exact rarity+shape, e.g. Blue + 1x2 → 7 matching rows shown), and directly via a contrived lot with one item of each partial-reveal kind (bypassing match RNG) confirming all three produce the exact expected filter object. The plain sidebar button still opens unfiltered (200/200 rows) and still toggles closed. Both regression suites still pass (36 + 37).

## Decided during Stage 1
- **Frontend stack:** vanilla JS (ES modules) + plain HTML/CSS, no build step/framework — simplest to host on GitHub Pages later, no tooling overhead.
- **Grid-packing algorithm:** randomized skyline/"bottom-left" packing, fixed 10-column width — items are placed in shuffled order so sizes scatter across the grid instead of clustering, while still keeping ~87% space utilization. (Originally shipped as sorted shelf-packing, changed after user feedback that it looked too size-sorted.)

## Decided during Stage 2
- See the "didn't pin down" callout above Stage 3 — Current Estimate formula, per-round "second-highest bid" semantics, Auctioneer Intel generation, placeholder bots/starting balance, sequential-not-blind local hotseat caveat.

## Decided during Stage 3
- See the callout above Stage 4 — effect dispatch shape (7 handlers + selection strategies, not per-device functions), all 17 sets / 8 assistants done in one pass rather than a partial subset, pre-match setup is free/no-currency for now, bots don't use devices yet.

## Decided during Stage 4
- See the callout above — Firestore over RTDB, single-document-per-room data model, room-code joining (no matchmaking), host-authoritative sync via an actions queue (no Cloud Functions/no paid plan), no Auth yet (sessionStorage-based identity instead), grid-packing computed once and synced rather than per-client.

## Post-Stage-4 — deployment
Deployed to GitHub Pages via a GitHub Actions workflow (`.github/workflows/deploy-pages.yml`) that publishes `app/` on every push to `main`, live at `https://ishananchit.github.io/NTE-Auction-Event/`. Repo excludes the local `images/` reference-screenshot folder (93MB, not needed for the live site) and `firebase.txt` (a scratch duplicate of `app/js/firebaseConfig.js`) via `.gitignore`.

**Firestore rules tightened** (`firestore.rules`, managed via the Firebase Console's Rules tab, not CLI-deployed — no `firebase.json` in this repo): replaced the wide-open test-mode default (which would have expired 2026-09-23) with structural validation — only the exact `rooms/{code}` + `rooms/{code}/actions/{id}` shape this app writes is allowed, field types/sizes are checked, and the `rooms` collection can't be enumerated (`allow get`, no `allow list`, so a room code must already be known). This is explicitly *not* per-player access control — there's still no Firebase Auth, so any client with the room code can still write any seat in that room, same as before. Real per-player enforcement (stopping one player from editing another's seat/bid) would need Anonymous Auth plus rules keyed off `request.auth.uid`; the user chose structural-only tightening for now given the friends-only threat model.
